# 鸽鸽词典 后续功能规划 — 竞品分析与 v1.1–v1.3 路线

文档状态：规划稿
适用版本：v1.0.0 之后
关联文档：`docs/PRD-v1.0.0-as-built.md`（当前实现基线）、`docs/PRD-v1.1-spec.md`（v1.1 开发规格）

### TL;DR

基于对 Saladict、Relingo、Trancy、Pot、openai-translator、Bob 六款同类产品的调研，鸽鸽词典所处的「桌面全局取词 + AI 词典级深度解析 + 本地生词沉淀」交叉点目前几乎无强竞品。后续规划的核心不是堆功能，而是先偿还 v1.0.0 遗留的体验与信任债（v1.1），再补上学习闭环这一最大功能缺口（v1.2），最后深化领域解析这一唯一护城河（v1.3）。同时明确列出八项不做的功能，避免在竞品的主场作战。

## 竞品分析

### 竞品矩阵

| 产品 | 形态 | 取词范围 | 解析深度 | 生词沉淀 | 数据归属 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| Saladict 沙拉查词 | 浏览器扩展 | 仅浏览器与内置 PDF | 多词典聚合，非 AI 语境解析 | 强，含 Anki Connect 自动制卡、WebDAV 同步 | 本地 + 可选 WebDAV | 活跃，开源 |
| Relingo | 浏览器扩展 + 移动端 | 仅浏览器 | 词汇高亮 + 释义，偏轻量 | 强，内置闪卡与间隔重复 | 云端账号 | 活跃，商业 |
| Trancy | 浏览器扩展 + 移动端 | 浏览器、流媒体字幕 | AI 单词分析 + 语境解析 | 强，闪卡 + AI 跟读评分 | 云端账号 | 活跃，商业 |
| Pot | 桌面全局 | 全系统 | 翻译为主，非词典式解析 | 弱，仅基础生词本 | 本地 | 已停止维护 |
| openai-translator | 桌面 + 扩展 | 全系统 | 翻译 / 润色 / 总结三模式 | 弱，词汇本较简单 | 本地 | 活跃，开源 |
| Bob | 桌面全局 | 全系统 | 插件化，依赖第三方插件 | 中等 | 本地 | 活跃，macOS 独占 |
| 鸽鸽词典 | 桌面全局 | 全系统 | AI 词典级深度解析 + 领域知识 | 中等，导出为主 | 完全本地 | v1.0.0 |

### 三个关键结论

结论一：市场是分层的，鸽鸽词典所在层几乎空缺。

Saladict、Relingo、Trancy 功能极强，但全部是浏览器扩展，出不了浏览器。用户在 IDE、Word、微信、远程桌面里读到英文时，这三款完全无能为力。Pot 与 openai-translator 覆盖全系统，但定位是翻译器，输出译文而非词典式结构化解析，生词本能力薄弱，且 Pot 已停止维护。Bob 是 macOS 独占。

因此「桌面全局取词 + 词典级深度解析 + 生词沉淀」这一交叉点目前没有强竞品，这是鸽鸽词典应当死守的位置。

结论二：领域知识扩展是六款产品里独此一家。

计算机、IVD 医疗、金融等专业领域的术语背景补充与代码示例，在所有竞品中均未见对应能力。这个特性目前只是 README 特性表里的一行，建议提升为主打卖点，并在 v1.3 系统性深化。

结论三：最大功能缺口是学习闭环断裂。

所有具备学习属性的竞品都有复习机制：Relingo 与 Trancy 内置闪卡与间隔重复，Saladict 通过 Anki Connect 自动制卡。而鸽鸽词典目前只能手动导出 TSV 再由用户自行导入 Anki，转化率极低。

后果是生词库沦为只进不出的数据坟场，PRD 中「平均沉淀 50 条形成迁移成本」的目标无法转化为真实黏性，W1 留存目标也难以成立。

## Goals

### Business Goals

* v1.1 发布后将剪贴板误触发率从当前水平降至日常使用一小时内不超过一次，消除卸载的首要诱因。
* v1.2 上线轻量复习后，使激活用户的生词库七日内回访率达到 30% 以上，验证闭环成立。
* 保持零服务端成本与零边际运营支出不变，全部新功能不得引入后端依赖。
* 在 v1.3 前将「领域深度解析」建立为可被外部识别的产品标签，体现在 README、Release 说明与社区讨论中。
* 建立应用内更新通道，使后续版本对存量用户的送达率不再依赖手动重装。

### User Goals

* 复制密码、代码、文件路径时不再被打断，也不必担心内容被发送至第三方服务。
* 长段落解析时能立即看到译文开始出现，而非面对数秒空白。
* 收藏的生词能在应用内被重新遇见，而不是存完即忘。
* 专业领域阅读时获得稳定一致的术语解析，而非每次随机发挥。
* 数据始终留在本机，且备份、迁移、恢复的路径清晰可靠。

### Non-Goals

* 不做多语种泛化，专注英汉方向。
* 不做浏览器扩展形态，不进入 Saladict 的主场。
* 不做云同步与账号体系，零服务端是信任资产而非技术妥协。

## 版本路线

### v1.1 — 体验与信任债偿还

定位：不加新功能，先把 v1.0.0 的坑填平。

理由：Ctrl+C 触发方式虽然兼容性优于 UI Automation，但误触发是该设计的原罪。用户复制密码、代码、文件路径都会弹窗并将内容发往第三方 LLM，这既是体验问题也是隐私事故。此问题不解决，留存指标做不上去，后续任何新功能都是沙上建塔。

| 编号 | 内容 | 优先级 | 工作量 |
| --- | --- | --- | --- |
| F0 | 修复数据目录迁移与备份的文件名不一致导致生词库丢失 | P0 | 0.5 天 |
| F1 | 接线本地缓存（后端已实现，仅需缓存键设计与调用） | P0 | 0.5 天 |
| F2 | 真流式渲染：SSE 双协议 + 增量 JSON 字段提取 | P0 | 3 天 |
| F3 | 剪贴板误触发治理与查词窗口行为改造 | P0 | 2.5 天 |
| F4 | API Key 改用 Windows DPAPI 加密存储 | P1 | 1 天 |

合计 8 个工作日，1 人。详细规格见 `docs/PRD-v1.1-spec.md`，对应 Issue #1 至 #5。

F0 需要特别说明：源码中数据目录迁移写入的文件名为 `lexnote.db`，而应用实际打开的是 `gege.db`。用户执行迁移后重启，程序会创建一个空库，表现为生词全部丢失。这是当前唯一的数据丢失级缺陷，必须优先处理。

### v1.2 — 补上学习闭环

定位：解决最大功能缺口，让生词库从存储变成使用。

核心原则是做轻量复习，但不做完整 SRS。完整的 SM-2 算法是在重复造轮子，正面对抗 Anki 没有胜算；但完全不做复习，生词库就没有存在意义。

主要内容：

* 轻量复习机制
    * 三档 Leitner 盒（新词 / 巩固中 / 已掌握），答对进阶，答错回退
    * 每日复习上限 20 词，避免堆积产生心理负担
    * 主窗口顶部常驻「今日回顾」入口，显示待复习数量
    * 保留 Anki 导出，供硬核用户继续使用既有工作流
* 阅读会话
    * 将同一时间段、同一来源应用的查词自动归为一次阅读会话
    * 会话视图可回顾「读这篇论文时查了哪些词」，还原学习场景
    * 支持按会话批量打标签与批量导出
* 应用内自动更新
    * 接入 Tauri updater，建立版本送达通道
    * 现在装机量尚小是植入成本最低的时刻，等用户基数上去再补需要所有人手动重装

预计工作量：Small，1 至 2 周，1 人。

### v1.3 — 深化护城河

定位：把唯一没有竞品的能力做深做稳。

主要内容：

* 个人术语表与领域 Profile
    * 用户可维护自己的术语表，指定特定词在特定领域下的固定译法
    * 解析时优先采纳个人术语表，避免同一术语每次翻译不一致
    * 领域 Profile 可切换（计算机 / 医疗 IVD / 金融 / 法律 / 通用），影响解析侧重与知识扩展方向
    * 支持术语表导入导出，便于团队内共享
* 截图 OCR 取词
    * 覆盖扫描版 PDF、视频字幕、远程桌面等无法复制文本的场景
    * 这是 Pot 的核心武器之一，也是当前 Ctrl+C 方案的能力天花板
    * 工作量约一周，如果实际使用中扫描件占比不高，可延后并把资源投给个人术语表
* 预设解析风格
    * 提供 2 至 3 套内置风格（简洁 / 标准 / 深度），替代完整的 Prompt 模板编辑器
    * 保留高级用户直接编辑模板的入口，但不作为主推功能

预计工作量：Medium，2 至 3 周，1 人。

## 明确不做的功能

以下八项在竞品中常见，但建议放弃或大幅降级。

| 功能 | 竞品情况 | 不做的理由 |
| --- | --- | --- |
| 多语种支持 | Pot 支持数十种语言 | 深度解析 Prompt 为英汉场景专门调优，泛化会稀释质量，且带来指数级的测试成本 |
| 浏览器扩展 | Saladict、Relingo、Trancy 主场 | 正面竞争无胜算，且会分裂技术栈与维护精力 |
| 云同步与账号体系 | Relingo、Trancy 标配 | 零服务端是核心信任资产。数据目录指向同步盘可解决约九成需求 |
| 完整 SRS 算法 | Anki、Relingo | 重复造轮子，v1.2 的三档 Leitner 已足够形成闭环 |
| 网页整页翻译 | 沉浸式翻译、Trancy | 桌面应用形态不适合，且与词典定位冲突 |
| 写作润色与语法纠错 | openai-translator | 通用 AI 助手能力，偏离词典定位，用户已有更好选择 |
| 真人发音音频 | Saladict | 涉及第三方授权，Windows TTS 已满足基本需求 |
| 本地用量统计面板 | 部分工具提供 | 用户真正关心的是账单，而账单在提供商控制台里，自建面板价值低 |

## Success Metrics

### User-Centric Metrics

* 剪贴板误触发率：日常使用一小时内非查词意图的弹窗次数，目标不超过 1 次。
* 首字段渲染时间：流式渲染下从触发到首个字段可见的耗时，目标 P50 小于 1 秒。
* 缓存命中率：重复查询命中本地缓存的比例，目标 20% 以上。
* 生词回访率：收藏后七日内在应用内被再次查看或复习的条目占比，目标 30% 以上（v1.2 后统计）。

### Business Metrics

* 版本送达率：接入自动更新后，存量用户在新版本发布两周内完成升级的比例，目标 60% 以上。
* GitHub Issue 中隐私与安全类反馈归零（v1.1 后）。
* 领域解析相关的正面提及出现在社区讨论或用户反馈中。

### Technical Metrics

* 数据迁移零丢失：迁移前后生词条目数完全一致。
* 流式解析降级成功率 100%，即流式失败时用户无感知回退。
* 敏感内容识别准确率：密码、密钥、路径、代码片段的拦截率 95% 以上，正常英文文本的误拦截率低于 2%。

### Tracking Plan

沿用 v1.0.0 的本地埋点原则，不做任何上传。新增事件：

* clipboard_filtered（含拦截原因：sensitive / blacklist / non_english / duplicate）
* clipboard_mode_changed（智能 / 全量 / 双击）
* lookup_cache_hit / lookup_cache_miss
* lookup_stream_first_field（记录首字段渲染耗时）
* lookup_stream_fallback（流式降级次数）
* review_session_started / review_card_answered / review_session_completed（v1.2）
* reading_session_viewed（v1.2）
* glossary_term_applied（v1.3）

## Technical Considerations

### Technical Needs

* v1.1 主要改动集中在 `clipboard_watcher.rs`、`llm.rs`、`db.rs` 三个模块，无架构级变更。
* v1.2 需新增复习状态表与阅读会话表，涉及数据库结构迁移，必须提供平滑升级路径。
* v1.3 的个人术语表需要在 Prompt 组装阶段注入，需评估对上下文长度的影响。

### Integration Points

* Tauri updater 需要配置更新服务器或使用 GitHub Releases 作为更新源，后者可维持零服务端原则。
* 截图 OCR 需选择本地 OCR 方案（如系统 OCR 或本地推理），避免引入云端依赖破坏隐私承诺。

### Data Storage & Privacy

* 所有新增数据（复习记录、阅读会话、个人术语表）继续存于本地 SQLite，不上传。
* 敏感内容识别在发送前完成，被拦截的内容不写入任何日志与缓存。
* 自动更新仅检查版本号与下载安装包，不上报任何用户数据。

### Potential Challenges

* 增量 JSON 解析是 v1.1 唯一有技术风险的部分，需准备降级预案。
* 复习功能一旦引入，就与「不做 SRS」的原 Non-Goal 冲突，需在文档中明确边界，避免范围蔓延为完整记忆系统。
* 个人术语表注入会增加每次请求的 token 消耗，需要设计按需注入策略而非全量携带。

## Milestones & Sequencing

### Project Estimate

* v1.1：Small，8 个工作日
* v1.2：Small，1 至 2 周
* v1.3：Medium，2 至 3 周

### Team Size & Composition

1 人全栈（Product + Engineering + Design 合一），配合 AI 编码助手。v1.0.0 即以此模式交付，后续无需扩编。

### Suggested Phases

阶段一：v1.1 体验与信任债偿还（8 个工作日）

* 关键交付：F0 至 F4 五项，详见 v1.1 开发规格。
* 建议顺序：F0（止血）→ F1（最快见效，并为 F2 调试提供缓存旁路）→ F2（风险最高，早开工留降级余地）→ F3 → F4。
* 依赖：无外部依赖。
* 成功标准：误触发率达标，首字段渲染进入 1 秒内，无数据丢失反馈。

阶段二：v1.2 学习闭环（1 至 2 周）

* 关键交付：三档 Leitner 复习、阅读会话、Tauri 自动更新。
* 依赖：数据库结构迁移需在 v1.1 稳定后进行。
* 成功标准：生词回访率达到 30%，自动更新通道验证可用。

阶段三：v1.3 护城河深化（2 至 3 周）

* 关键交付：个人术语表与领域 Profile、预设解析风格；截图 OCR 视优先级决定是否纳入本阶段。
* 依赖：术语表注入策略需先完成 token 消耗评估。
* 成功标准：同一术语在多次查询中译法稳定一致；领域解析成为可被外部识别的产品标签。
