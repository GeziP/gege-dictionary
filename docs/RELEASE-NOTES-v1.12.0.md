# 鸽鸽词典 V1.12.0

本版本只换一件事：**截图 OCR 取词的识别引擎**。从 Windows 自带的 OCR 换成随安装包分发的 PP-OCRv6 + ONNX Runtime：不再需要 OCR 语言包，也不用去改系统语言设置，中文和英文都能读。其余功能没有变化，也没有数据库升级。

## 为什么换

v1.11.1 修好了黑屏，但留下一个说不通的前提：Windows 的 OCR 只认电脑上**已经装好的语言包**。中文系统通常只有中文这一个，读英文时只能让中文引擎硬读，读出来的是 `He110`、`Librany'`、`00g`。v1.11.1 的办法是在提示卡上让用户去「设置 → 时间和语言」添加 English、勾选「光学字符识别」，这等于要求每个用户改自己的系统设置——公司电脑、没有管理员权限、不想动系统的人都做不到。

开发机（只装了中文 OCR 语言包）上用同一批样本对比：

| | 合成的英文样本（词） | 真实网页截图（词） | 很紧的小框（单个词、字幕） |
| --- | --- | --- | --- |
| Windows 中文引擎读英文（v1.11.1 的实际行为） | 80 / 120（67 %） | 393 / 481（82 %） | 原尺寸下什么也读不出 |
| PP-OCRv6 tiny（本版） | 120 / 120 | 483 / 489（99 %） | 读得出 |

Windows 引擎读出来的是 `lnformal`、`ThiS`、`beCaUSe`、`exa ple` 这类东西。注意这里比的是「没装英文包的中文系统」会得到什么；Windows 自己的英文引擎没有比：开发机没装英文包，我也不为了测试去改这台机器的系统设置。

## 变化

### 截图取词用内置引擎读

- **引擎**：检测和识别两个小网络（PP-OCRv6 tiny，Apache-2.0，来自百度 PaddleOCR 项目，合计约 6.3 MB）编进程序，由随包的 ONNX Runtime 1.24.4（MIT）在本机 CPU 上运行。识别这一步不联网，不要语言包，不要管理员权限，不动系统设置。
- **中英文都读**，混排也读，行序按屏幕上的阅读顺序拼接；不再有「识别语言」可选。字符表约 6900 个：约 6200 个汉字（以简体为主，常用繁体字大多也有）、英文、数字、常用标点和希腊字母。
- **小框和浅色字**：Windows 引擎在原尺寸下读不出的单个词、视频字幕、深色底浅色字，现在能读（见下面的实机验收 B4、B5）。
- 框选页的提示改成「拖拽框选要识别的文字（中英文都行），Esc 或右键取消」。

### 「检测 OCR 可用性」真的读一遍

- 以前只是问系统「有没有这个语言」。现在是真画一句话（`The quick brown fox jumps over the lazy dog`），让引擎读一遍：9 个词里读对 7 个以上算通过，并写出「读出了 N/9 个词，用时 … 毫秒」。没通过时，画的是什么、读出来的是什么都会写在提示里。
- 检测期间按钮显示「检测中…」，不会连点两次。

### 去掉的东西

- 框选窗上「缺识别包」的提示卡和设置页的「打开系统语言设置」按钮：没有语言包这回事了。引擎出了问题时，框选窗里只有一段说明和「关闭」。
- 设置项 `ocr.language`：旧值留在数据库里无害，不再被读取。
- 对 Windows OCR 组件（`Windows.Media.Ocr`）的全部调用，以及随之而来的 WinRT / COM 依赖特性。

### 用到才载入，不白占内存

- 启动应用时不载入引擎；按热键打开框选窗时在后台预热，所以从按热键到出现冻结画面不会变慢；闲置约 2 分钟后自动释放。
- 关闭了 ONNX Runtime 的 CPU 内存池，否则读几次真实截图后常驻会涨到 220–540 MB。现在读完之后常驻约 40–50 MB，读很大的区域时瞬间峰值约 250–275 MB，读完回落。线程数取 CPU 核数的一半，限制在 2–4 个，不会把所有核占满。
- 开发机（12 核）上的速度：载入引擎约 0.17 秒（动态库约 30 毫秒 + 建会话约 145 毫秒），第一次读约 0.25 秒；之后常见的小框 10–130 毫秒，一整栏（约 1240×1510 像素）约 0.5–0.6 秒。

### 出了问题看得见，也不会就此卡死

- 引擎载入失败会给出具体原因，并建议重新安装；**失败不会被记住**，把文件修好（例如从杀毒软件的隔离区放回 `onnxruntime.dll`）后下一次识别就恢复，不用重启应用。
- 识别过程中引擎内部出错（panic）会被隔离、引擎被重置，提示「已经重置，请再试一次」，不会让应用崩掉。

## 工程

- 新增 `src-tauri/src/ppocr/`：检测输出的后处理（连通域、最小外接矩形、膨胀）、透视裁剪、识别分批、CTC 解码、阅读顺序拼接，全部自己写在 `ort` 上；新增 `src-tauri/src/ocr_engine.rs`：懒载入、预热、闲置释放、panic 隔离。没有用现成的 `oar-ocr` 之类的封装，因为它们没法关掉 ONNX Runtime 的 CPU 内存池，常驻内存降不下来。
- `ort 2.0.0-rc.13` 用 `load-dynamic`：ONNX Runtime 不静态链进程序，也不带 DirectML（那样会让主程序多出 28 MB 和一串硬依赖）；运行时按绝对路径载入程序旁边的 `onnxruntime.dll`。
- 运行库的取得：`src-tauri/ort-runtime.json` 固定 PyPI 官方 wheel 的下载地址、整个 wheel 和 DLL 的 SHA-256；`scripts/fetch-onnxruntime.ps1` 下载、逐项核对，并把构建机上 Visual Studio 里最新的那份四个 VC++ 运行库一起放进 `src-tauri/resources/ort/`（git 忽略）；运行库不能比链接这个 DLL 的工具集（读自 DLL 头，这一版是 14.44）更旧，更旧时脚本直接停下。`ci.yml` 和 `release.yml` 在 `npm ci` 之后新增一步运行它。`build.rs` 在缺 `onnxruntime.dll` 时直接停下，并提示运行这个脚本，不会悄悄打出一个没有引擎的包。
- 模型文件 `det.onnx`、`rec.onnx`、`dict.txt` 在 `src-tauri/models/pp-ocrv6/`，用 `include_bytes!` 编进程序；字节与 PaddleX 官方发布的 ONNX 推理包一致，有测试逐个核对 SHA-256；`.gitattributes` 把它们标为二进制，不会被换行转换改动。
- 许可：新增 `THIRD-PARTY-NOTICES.md`；`licenses\` 文件夹随安装包放在程序旁边（Apache-2.0 全文、模型的署名说明、ONNX Runtime 的 MIT 与第三方声明、运行库来源说明）。
- 版本三处同步 1.12.0（`package.json`、`src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json`，两个锁文件随之更新）。
- 前端测试 47 个文件 740 项（比 v1.11.1 少 2 项：删掉的是语言包相关的用例）；Rust 单元测试 383 项（比 v1.11.1 多 60 项：识别管线 45、引擎生命周期 12、OCR 本身净增 3，包含真实画一句话再读出来、从整屏画面里切一块再读、安装包资源清单与 `tauri.conf.json` 一致等）。

## 升级说明

- **没有数据迁移**：schema 仍是 v7，设置不变，应用内更新即可。退回 v1.11.1 不需要处理数据目录。
- **不用再装 OCR 语言包**。已经装好的也不再被用到，不会冲突。
- 安装包从 5.18 MB 变为 14.62 MB，安装后多占约 23 MB 磁盘。程序旁边会多出 `onnxruntime.dll`（约 16 MB）、四个 Visual C++ 运行库 DLL（`vcruntime140.dll`、`vcruntime140_1.dll`、`msvcp140.dll`、`msvcp140_1.dll`，合计不到 1 MB）和 `licenses\` 文件夹；卸载时一并删除。这些运行库按 Microsoft 允许的「随应用部署」方式放在程序自己的目录里，不会改系统的 Visual C++ 运行库。
- 第一次识别（以及闲置两分钟后的第一次）会慢一点，开发机上约 0.25–0.4 秒：引擎在按下热键时就开始在后台载入，通常框选完成时已经载好。
- 识别这一步不联网；识别出的文字之后和复制的文字走同一条查词流程，所以查词仍然会连你配置的模型服务，这是原有行为。
- 框选时看到的仍是按下热键那一刻的静止画面，截图只在内存里，不写磁盘，不上传。

## 已知问题

- 字符表里没有日文假名和韩文，读日文、韩文的文字会读成相近的汉字或乱码。
- 繁体字只覆盖一部分：抽查 57 个常用繁体字，46 个在字符表里；缺的多是「言」字旁的字，例如「說」「詞」「論」「認」「議」「讓」，它们会被读成相近的字。
- 只按横排读：竖排文字（比如竖排的中文）会读错。
- 很小的字号（约 10 像素以下）、艺术字和手写体可能读错。
- 杀毒软件或企业安全策略如果拦截、隔离了 `onnxruntime.dll`，框选窗会提示「找不到 OCR 运行库」并建议重新安装；把文件放回去，下一次识别就恢复。
- DRM 保护的视频、个别银行类客户端的窗口，系统不允许截屏，这些区域在画面里是黑的；框到的区域是纯色时，提示里会说明这一点。这是系统限制。
- 沿用 v1.11.0：界面样式里引用的网络字体被内容安全策略挡住，安装版显示系统后备字体。本版没有改动。

## 验证

开发机上的自动化检查通过：`npx tsc --noEmit`、`npm run lint`、`npm run build`、`npx vitest run`（47 个文件 740 项）、`cargo fmt --check`、`cargo clippy --locked --all-targets -- -D warnings`、`cargo test --locked`（383 项）。

GitHub 的 `windows-latest` 上，CI 也通过了：`Fetch ONNX Runtime` 一步下载、核对并选出构建机上最新的 Visual C++ 运行库（那台构建机上有 14.29、14.44、14.51 三份，选的是 14.51），`cargo test` 的 383 项在这套运行库上全部通过，其中包括真的载入 ONNX Runtime、画一句话再读出来的测试。

引擎本身：同一批模型在 Python 参考实现和这里的 Rust 实现里读同一批样本，结果一致（真实网页都是 483/489 词）；Rust 一侧的合成样本读出 100/102 词，差的两个词是一处空格（`I cannot` 读成 `Icannot`），不是读错的字。

打包：在开发机上用 `tauri build` 打出过安装包（14.62 MB），并核对了 NSIS 脚本里的文件清单：`onnxruntime.dll`、四个运行库 DLL 和 `licenses\` 都落在程序旁边。**没有运行安装包，也没有运行打出来的应用**，因为那会在开发机上注册一个应用，并碰到正在使用的那一份的数据目录。

所以下面这些没有被验证过，请按 `docs/QA-machine-checklist-v1.12.md` 在 Windows 实机验收：

- 在**没装英文 OCR 识别包**的电脑上按热键框选一行英文，查得到词，全程没有任何要求改系统语言的提示（A3、B1）。
- 没装过 Visual C++ 运行库的干净机器上能用（D3）；开发机上装着系统的运行库，不能代表这种情况。
- 在装着 v1.11.1 的机器上应用内更新到 1.12.0，设置、生词库、API Key 都在（A1）。
- 识别一次后内存增加约 50 MB，闲置两分钟后回落（C1–C3）；读一整页时在 1–2 秒内出结果（B6）。
- 识别时没有网络请求（E1）。
- 真实的热键和托盘入口、多屏与混合缩放（沿用 v1.6 清单 B 组，B7）。
